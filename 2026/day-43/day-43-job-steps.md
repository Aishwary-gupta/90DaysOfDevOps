## What I Learned

### Jobs

A job is a collection of steps that runs on a GitHub Actions runner.

Example:

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
```

A workflow can contain multiple jobs.

### Steps

A step is an individual operation inside a job.

Example:

```yaml
steps:
  - name: Build application
    run: echo "Building"

  - name: Run tests
    run: echo "Testing"
```

A job can contain multiple steps.

## Job Dependencies

The `needs` keyword controls the order in which jobs execute.

Example:

```yaml
test:
  needs: build
```

This means the `test` job waits for the `build` job to complete successfully.

A complete dependency chain can look like:

```text
Build
  |
  v
Test
  |
  v
Deploy
```

Multiple jobs can also run in parallel:

```text
       +--- Lint ---+
       |            |
Push --+            +---> Summary
       |            |
       +--- Test ---+
```

Example:

```yaml
summary:
  needs: [lint, test]
```

## Environment Variables

Environment variables allow configuration values to be made available to workflows, jobs, or individual steps.

### Workflow Level

```yaml
env:
  APP_NAME: myapp
```

Available throughout the workflow.

### Job Level

```yaml
jobs:
  build:
    env:
      ENVIRONMENT: staging
```

Available inside that job.

### Step Level

```yaml
- name: Show version
  env:
    VERSION: 1.0.0
  run: echo "$VERSION"
```

Available only to that step.

## GitHub Context Variables

GitHub Actions provides context variables containing information about the workflow execution.

Examples:

```yaml
${{ github.sha }}
```

Returns the commit SHA.

```yaml
${{ github.actor }}
```

Returns the user or actor that triggered the workflow.

## Job Outputs

Job outputs allow information generated by one job to be passed to another job.

Example:

```yaml
generate:
  outputs:
    today: ${{ steps.date.outputs.today }}
```

The value can then be consumed by another job:

```yaml
${{ needs.generate.outputs.today }}
```

This is useful when one job generates information required by a later job.

Examples include:

* Version numbers
* Build IDs
* Generated file names
* Environment information
* Deployment information

## Conditionals

GitHub Actions allows steps and jobs to run only when specific conditions are satisfied.

Example:

```yaml
if: github.ref == 'refs/heads/main'
```

This can be used to execute a step only when the workflow is running on the `main` branch.

Another useful condition is:

```yaml
if: failure()
```

This allows a step to run when a previous step has failed.

## continue-on-error

`continue-on-error: true` allows a step to fail without stopping the rest of the workflow.

Example:

```yaml
- name: Optional check
  continue-on-error: true
  run: exit 1
```

The step is marked as failed, but subsequent workflow execution can continue.

## Important GitHub Actions Concepts

| Concept             | Purpose                                                    |
| ------------------- | ---------------------------------------------------------- |
| Job                 | Group of work executed on a runner                         |
| Step                | Individual command or action                               |
| `needs`             | Creates dependencies between jobs                          |
| `outputs`           | Passes information between jobs                            |
| `env`               | Defines environment variables                              |
| `if`                | Controls conditional execution                             |
| `continue-on-error` | Allows workflow execution to continue after a step failure |

## Smart Pipeline Architecture

The final workflow used two independent jobs followed by a summary job.

```text
                 +--- Lint ---+
                 |            |
Push ------------+            +----> Summary
                 |            |
                 +--- Test ---+
```

The `lint` and `test` jobs can execute in parallel.

The `summary` job waits for both jobs using:

```yaml
needs: [lint, test]
```

## Key Learnings

1. `needs` is used to control job dependencies.
2. `outputs` allows data to move between jobs.
3. Environment variables provide configuration values at workflow, job, and step levels.
4. Conditional expressions allow workflows to behave differently depending on branches, events, or previous results.
5. Independent jobs can run in parallel, which can reduce CI execution time.
